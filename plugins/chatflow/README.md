# Chat flow (`chatflow`)

The foreground flow: a router, parallel host reads from the code graph, missing-first decide, then answer / do / delegate, and the coding agent loop over read, edit and run with impact injection after signature changes, steering at tool boundaries, follow-up queues, cancellation and repetition stop. Prompts, stages and schemas are data (`backend/data/`, compiled in). The UI packages are the conversation (`workbench.chat@1`) and the composer (`chat.composer@1`).

One self-contained plugin folder, separable into its own repository (only `cc-protocol` and `@cortex/sdk` come from outside):

| Path | What |
|---|---|
| `plugin.toml` | identity, build commands and outputs, UI packages and their slots, shell modules, source location |
| `backend/` | Cargo workspace (depends on `cc-protocol` by path), binary `cc-chatflow`: category `chatflow`, contract `chatflow@1` |
| `ui/` | one npm workspace (own `package-lock.json`, `@cortex/sdk` as a local dependency): `ui/chat` (workbench.chat@1), `ui/composer` (chat.composer@1); each package builds `dist/` with `manifest.json` |

## Attachments

The composer attaches pasted screenshots, dropped or picked files and whole folders. `chatflow.attachment.put` (the shape of the planned `frame.attachment.put`: `{sha256, path, mime, size, width?, height?}`) stores bytes content-addressed in `$CORTEX_HOME/attachments/<sha256>.<ext>` (the shell writes pasted bytes to `attachments/incoming/` first, so they never travel base64 over CPP; base64 `data` is the fallback without a shell), references files and folders of the project by path (nothing copied, nothing written into the repository) and copies other files into the store. `chatflow.turn` / `chatflow.steer` (and `agents.steer`) carry `attachments`, journaled on the `user_message` / `steer` entry; a folder gets its top-level listing and an image its dimensions when journaled (`backend/src/attachments.rs`). The model reads them as paths after the message text. Images: `attachments::vision_hook` asks a `vision.describe` capability when one serves it (none does yet: no description is ever made up); when `model.info` advertises `extra.input_modalities: ["image"]`, user messages also carry the images as `model@1` content parts.

## Cross-project references

docs/IDEATION-WORKFLOW.md part 2 (`backend/src/references.rs`). The composer completes `@<project>` from `memory.project.list` and `@<project>:<symbol>` from `memory.search` scoped to that project; every message carries them as `mentions` (`{project, symbol?}`): `chatflow.turn` (journaled on the `user_message`), `chatflow.steer` and `agents.steer` (journaled on the `steer` entry and carried to the `user_message` a steer or follow-up becomes; the note goes to the running run, with `steer_seq`). A folder attachment outside the session's project and workspace that is a known project's root or has a `.git` entry counts as the same. Each referenced project is opened read-only (`memory.project.open` with `reference: true`, indexed in the background), a mentioned symbol is resolved now (`memory.symbol`) when its graph is ready, and the run gets one host note (`purpose: references`): each project's root, its qualified URIs (`graph://<project>/...`, `symbol://<project>/<name>`, `outline://`, `definition://<project>:...`, the read target `<project>:<path>`) and each symbol's location; an unknown name or a failed open is named, never guessed. Memory is asked once per call, without retries. Texts: `references*` in `backend/data/texts.toml`.

## Prompt layout

`backend/src/prompts.rs`, words in `backend/data/`. The system prompt is byte-stable per session and role (`stages.toml` `[protocol]`): a chat session's carries the policy and the rules of ROUTE, DECIDE, REPLY, DO and ASK; a background agent's only TASK's. A stage outside its role's list (CHECKS, SPEC, SPEC_EDIT, PLAN, PLAN_EDIT, DECISIONS) carries its rules in its own trailing stage message, without the rule parts its role's prompt already has (a stage's `rules` may list several prompts: `check_rules` is shared by DECIDE, CHECKS and PLAN). Short JSON decisions (ROUTE, DECIDE, CHECKS, DECISIONS, SPEC_EDIT) are greedy (`sampling.decision`). Host reads are shown under the target the model's own `read` would take (`graph://search/...`, `symbol://...`, a file path; `reads::read_target`).

## Skills

`backend/src/skillsel.rs` (R1-R4). The turn's first generation chooses: ROUTE writes `work`, then `route`, then `skills` on ANSWER, LOOKUP, DO, DELEGATE and PLAN (`router.json` `x-when`; STATUS chooses none, IMPLEMENT runs each plan task with that task's own skills), an enum of the session's catalog (previous turn's skills first), capped by `limits.skills_per_turn`. The catalog (uri and summary per skill) is part of a chat session's system message (`limits.skills_in_prefix = true`, see Prewarm), or, with `false`, shown only in the trailing stage message of the stages that choose (ROUTE, and PLAN / PLAN_EDIT for each task's `skills`). The rule (`prompts/route.md`) is a measured one: a skill applies when its summary names the work stated in `work`. The chosen skills are injected once, right after ROUTE and before anything else of the turn (spec, reads, DECIDE, the tool loop, REPLY, PLAN), as a host note (`purpose: skills`, `decision_seq` = the route entry): the first in full, the others by catalog line. DECIDE chooses none, so a DECIDE that changes the route keeps ROUTE's skills; DELEGATE passes them to the agents (`delegate_skills`). `read skill://...` stays available mid-work. DECIDE writes `brief` only on DELEGATE and PLAN (`decide.json` `x-when`), for a reader outside the conversation; the DO loop runs in the conversation, from the statement and the reads, never from a restatement of them (a restated contract outranked the statement in the model's eyes), and its foreground task is named by ROUTE's `work`. ROUTE's `work` sentence itself is not shown to the model either (`projection::describe_decision`): it serves the UI, the memory search and a delegated agent's context.

## Prewarm and live feedback

`backend/src/prewarm.rs`, `backend/src/live.rs`. Every call of a session starts with the same system message (with the skills catalog when `limits.skills_in_prefix`, the default: session order, so it is cached across turns; ROUTE's stage message then names only the previous turn's skills) and the projected conversation (`prewarm::conversation`, the one builder every call uses). `chatflow.prewarm` (the chat UI calls it when a conversation is opened and, debounced, while the person writes; the flow itself when a turn ends) prefills that prefix closed by a placeholder message (`model.prewarm`, background priority) once per session state (a hash of the exact request), so the next ROUTE reads only the new message and its stage message. The model plugin stops a prewarm when a real request for the conversation arrives, and the next turn cancels it. While a constrained decision streams, its free-text fields (the schema's top-level strings: ROUTE's `work`, DECIDE's `missing`, `brief`, `note`) are published as `chatflow.live` (at most every 250 ms, a last one `done`). The chat's working line shows them with `model.progress` ("Reading the conversation · 4,200 / 9,800 tokens", "Writing · 120 tokens · 41 tok/s"); a turn's steps, reasoning and notes for the model fold into one activity line per run of work, in the order it ran, with the model's prose after the line it followed; while a command runs the line shows it with its elapsed time and the output it has printed so far (`tool_call.live_output`, appended by the loop as the tools plugin streams it); a finished turn ends with a card of the files it edited (counts per file, the diffs, and Undo, which reverse-applies the turn's own hunks). `verify/live.mjs` checks all of it through the real frame against the scripted model (DEBUG builds).

## Spec, decisions, plans

The composable parts of docs/IDEATION-WORKFLOW.md (1, 5, 6), each usable alone (`backend/src/spec.rs`, `backend/src/plan.rs`, stages in `flow.rs`, rules and schemas in `backend/data/`):

- **Spec.** A message becomes the session's spec structurally (text longer than `limits.spec_min_chars` while there is none, or marked with the composer's Spec toggle) or by the router's `spec` field (`new`, `amend`). SPEC extracts the requirements (`R1`...) in one constrained call; SPEC_EDIT applies a later message's changes (added, dropped, changed ids; the id enum is the spec's own). Every change is a `spec` entry (a version); its number is its place among the `spec` entries in append order (corrected on the entry right after the append), so a user edit and a model amendment landing together get distinct versions, and SPEC_EDIT applies to the spec as it is after its model call. The model sees the current spec whole right after the system prompt (never folded, counted by the fit); its source message is shown as a reference. DECIDE and CHECKS get the open ids, the DO loop is asked to end with coverage per requirement. `chatflow.spec.update` (the spec card's edits) makes a version by the user; `chatflow.spec.save` writes `docs/specs/<slug>.md`.
- **Decisions.** The router's `settles` field runs DECISIONS after the answer: `decision` entries the user accepts or rejects (`chatflow.decision.answer`). Accepted ones join the spec (a version) or, without a spec, are pinned as the session's decision list, and are written to the project's knowledge as `decision` items (`memory.knowledge.upsert`; the entry keeps the `knowledge_id`; memory being away never fails the answer).
- **Knowledge** (docs/PROJECT-KNOWLEDGE-PLAN.md P2–P4; the store is the memory plugin's, on IronGraph). *Write side:* the router's `teaches` field (yes when the message states something durable about the project's world, or asks to remember) runs KNOWLEDGE after the answer and after DECISIONS: one constrained call (`schemas/knowledge.json`, `prompts/knowledge.md`) writes at most `limits.knowledge_items_per_turn` items (`kind` concept | fact | hypothesis | question, `name`, `text`, `state`, `binds`); the `binds` pick is filled by the host with the code the turn saw (`flow::turn_binds`: the route's symbols and files, the host's symbol, outline and file reads, the model's own `read` and `edit` paths, never a URI), so an item never names code nobody looked at, and the host keeps a `state` only when the kind allows it. Each item is a `knowledge` journal entry (a card: Keep with the text as edited, or Don't keep; `chatflow.knowledge.answer`); nothing is stored before the answer. Keep writes the item with `source: user`, the journal entry as evidence and `implemented_by` (a concept) or `about` links to its bound code. *Read side:* (1) what is bound to the code a host read serves rides along with it, one line per item appended to the read's output (`reads::knowledge_lines`, `memory.knowledge.linked` by the symbols' sids, or the outline's and file read's path; the tools plugin does the same for the model's own `read`, and serves `knowledge://<id>`); (2) after the first round's reads, one `memory.knowledge.search` with ROUTE's `work` sentence, at most `limits.knowledge_per_turn` items, as one host note (`purpose: knowledge`, `flow::knowledge_note`), items whose text the brief already holds left out, nothing when nothing is found; (3) the brief: `memory.knowledge.brief` within `limits.brief_tokens` (0 = none) in the byte-stable system prompt (`section_knowledge`, after the style, before the repository map), computed once per session with the rest of the prefix, so it is cached and prewarmed and the next session sees what was learned since.
- **Planned changes.** A decided change (DECIDE's DO) is planned before it is made: the PLAN stage runs with `plan_auto_live` (its tasks are carried out at once, one per run of the DO loop, by the conversation's own loop), the plan entry is recorded as `implementing` with the run as `implement_run`, and the Act stage makes the plan's tasks memory tasks under a root task (`materialize_plan_tasks`, the same records the agents path uses: the board and the cards show them) and runs them one at a time in order (`Stage::Act { step }`): each loop gets its task's title and brief and what the earlier tasks did (`agent_loop::step_live`, `do_step`, `do_task_text`), the task's contract (the last one's joined by the decision's checks) is verified before the next starts, the model's reply ends the task, its outcome is recorded on the plan entry (`steps_done`: the chat card marks done, failed and current tasks) and on the memory task (`memory.task.update`). A plan without tasks, or an IMPLEMENT decision (made from a plan), runs as one loop.
- **Plans.** Route PLAN (ROUTE and DECIDE; ROUTE's `skills` serve the planner only) runs PLAN, or PLAN_EDIT while a plan is open: a `plan` entry with the document and a task graph (numbered dependencies on earlier tasks only, touches, checks from the project's verifiers, covered requirement ids, and the task's own `skills` from the session's catalog, capped by `limits.skills_per_turn`), nothing changed. An edit is a new version with its difference. `chatflow.plan.update` approves; Implement (`chatflow.plan.implement`, or the router's IMPLEMENT, offered only while a plan is open) runs a single task in the foreground loop with its contract and its skills, or makes memory tasks (each brief naming that task's skills) with contracts and dependencies under a root task and starts the ready ones with `agents.spawn`. The chat panel draws the spec card (pinned), decision cards and plan cards (task progress from `agent_spawned` / `verification`).

## Build and run

```sh
cd backend && cargo build --release && cargo test --release && cargo clippy --all-targets -- -D warnings
cd ui && npm ci && npm run build && npm test     # after the SDK is built (cd ../../ui/sdk && npm run build)
cortex-pack build plugins/chatflow                  # -> plugins/chatflow/target/chatflow-<version>-<target>.ccplugin
```

`cortex-pack build plugins/chatflow --install` packs the folder into a `.ccplugin` that the frame installs (`frame.plugins.install`), which hot-swaps the backend and the UI packages together; Settings > Plugins disables and enables the whole plugin.

## Verification

The mechanics are verified together with the agents plugin: ../agents/verify/mechanics.mjs (gate 1.6 G3), against deterministic test peers (../runtime-testpeers) through the real frame. Its section 15 is `verify/ideation.mjs` (spec, decisions, plan mode) and section 16 `verify/references.mjs` (cross-project references); each also runs alone.
