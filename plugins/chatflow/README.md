# Chat flow (`chatflow`)

The foreground flow: a router, parallel host reads from the code graph, missing-first decide, then answer / do / delegate, and the coding agent loop over read, edit and run with impact injection after signature changes, steering at tool boundaries, follow-up queues, cancellation and repetition stop. Prompts, stages and schemas are data (`backend/data/`, compiled in). The UI packages are the conversation (`workbench.chat@1`) and the composer (`chat.composer@1`).

One self-contained plugin folder, separable into its own repository (only `cc-protocol` and `@cortex/sdk` come from outside):

| Path | What |
|---|---|
| `plugin.toml` | identity, build commands and outputs, UI packages and their slots, shell modules, source location |
| `backend/` | Cargo workspace (depends on `cc-protocol` by path), binary `cc-chatflow`: category `chatflow`, contract `chatflow@1` |
| `ui/` | one npm workspace (own `package-lock.json`, `@cortex/sdk` as a local dependency): `ui/chat` (workbench.chat@1), `ui/composer` (chat.composer@1); each package builds `dist/` with `manifest.json` |

## Attachments

The composer attaches pasted screenshots, dropped or picked files and whole folders. `chatflow.attachment.put` (the shape of the planned `frame.attachment.put`: `{sha256, path, mime, size, width?, height?}`) stores bytes content-addressed in `$CORTEX_HOME/attachments/<sha256>.<ext>` (the shell writes pasted bytes to `attachments/incoming/` first, so they never travel base64 over CPP; base64 `data` is the fallback without a shell), references files and folders of the project by path (nothing copied, nothing written into the repository) and copies other files into the store. `chatflow.turn` / `chatflow.steer` (and `agents.steer`) carry `attachments`, journaled on the `user_message` / `steer` entry; a folder gets its top-level listing and an image its dimensions when journaled (`backend/src/attachments.rs`). The model reads them as paths after the message text. Images: `attachments::vision_hook` asks a `vision.describe` capability when one serves it (none does yet: no description is ever made up); when `model.info` advertises `extra.input_modalities: ["image"]`, user messages also carry the images as `model@1` content parts.

## Cross-project references

docs/IDEATION-WORKFLOW.md part 2 (`backend/src/references.rs`). The composer completes `@<project>` from `memory.project.list` and `@<project>:<symbol>` from `memory.search` scoped to that project; every message carries them as `mentions` (`{project, symbol?}`): `chatflow.turn` (journaled on the `user_message`), `chatflow.steer` and `agents.steer` (journaled on the `steer` entry and carried to the `user_message` a steer or follow-up becomes; the note goes to the running run, with `steer_seq`). A folder attachment outside the session's project and workspace that is a known project's root or has a `.git` entry counts as the same. Each referenced project is opened read-only (`memory.project.open` with `reference: true`, indexed in the background), a mentioned symbol is resolved now (`memory.symbol`) when its graph is ready, and the run gets one host note (`purpose: references`): each project's root, its qualified URIs (`graph://<project>/...`, `symbol://<project>/<name>`, `outline://`, `definition://<project>:...`, the read target `<project>:<path>`) and each symbol's location; an unknown name or a failed open is named, never guessed. Memory is asked once per call, without retries. Texts: `references*` in `backend/data/texts.toml`.

## Prompt layout

`backend/src/prompts.rs`, words in `backend/data/`. The system prompt is byte-stable per session and role (`stages.toml` `[protocol]`): a chat session's carries the policy and the rules of ROUTE, DECIDE, REPLY, DO and ASK; a background agent's only TASK's. A stage outside its role's list (CHECKS, SPEC, SPEC_EDIT, PLAN, PLAN_EDIT, DECISIONS) carries its rules in its own trailing stage message, without the rule parts its role's prompt already has (a stage's `rules` may list several prompts: `check_rules` is shared by DECIDE, CHECKS and PLAN). Short JSON decisions (ROUTE, DECIDE, CHECKS, DECISIONS, SPEC_EDIT) are greedy (`sampling.decision`). Host reads are shown under the target the model's own `read` would take (`graph://search/...`, `symbol://...`, a file path; `reads::read_target`).

## Skills

`backend/src/skillsel.rs` (R1-R4). The turn's first generation chooses: ROUTE writes `work`, then `route`, then `skills` on ANSWER, LOOKUP, DO, DELEGATE and PLAN (`router.json` `x-when`; STATUS chooses none, IMPLEMENT runs each plan task with that task's own skills), an enum of the session's catalog (previous turn's skills first), capped by `limits.skills_per_turn`. The catalog (uri and summary per skill) is part of a chat session's system message (`limits.skills_in_prefix = true`, see Prewarm), or, with `false`, shown only in the trailing stage message of the stages that choose (ROUTE, and PLAN / PLAN_EDIT for each task's `skills`). The rule (`prompts/route.md`) is a measured one: a skill applies when its summary names the work stated in `work`. The chosen skills are injected once, right after ROUTE and before anything else of the turn (spec, reads, DECIDE, the tool loop, REPLY, PLAN), as a host note (`purpose: skills`, `decision_seq` = the route entry): the first in full, the others by catalog line. DECIDE chooses none, so a DECIDE that changes the route keeps ROUTE's skills; DELEGATE passes them to the agents (`delegate_skills`). `read skill://...` stays available mid-work. DECIDE writes `brief` only on DELEGATE and PLAN (`decide.json` `x-when`), for a reader outside the conversation; the DO loop runs in the conversation, from the statement and the reads, never from a restatement of them (a restated contract outranked the statement in the model's eyes), and its foreground task is named by ROUTE's `work`. ROUTE's `work` sentence itself is not shown to the model either (`projection::describe_decision`): it serves the UI, the memory search and a delegated agent's context.

## Prewarm and live feedback

`backend/src/prewarm.rs`, `backend/src/live.rs`. Every call of a session starts with the same system message (with the skills catalog when `limits.skills_in_prefix`, the default: session order, so it is cached across turns; ROUTE's stage message then names only the previous turn's skills) and the projected conversation (`prewarm::conversation`, the one builder every call uses). `chatflow.prewarm` (the composer calls it, debounced, while the person writes; the flow itself when a turn ends, then only while the model has nothing else to do; opening a conversation loads nothing) prefills that prefix closed by a placeholder message (`model.prewarm`, background priority) once per session state (a hash of the exact request), so the next ROUTE reads only the new message and its stage message. The model plugin stops a prewarm when a real request for the conversation arrives, and the next turn cancels it. While a constrained decision streams, its free-text fields (the schema's top-level strings: ROUTE's `work`, DECIDE's `missing`, `brief`, `note`) are published as `chatflow.live` (at most every 250 ms, a last one `done`). The chat's working line shows them with `model.progress` ("Reading the conversation · 4,200 / 9,800 tokens", "Writing · 120 tokens · 41 tok/s"); a turn's steps, reasoning and notes for the model fold into one activity line per run of work, in the order it ran, with the model's prose after the line it followed; while a command runs the line shows it with its elapsed time and the output it has printed so far (`tool_call.live_output`, appended by the loop as the tools plugin streams it); a finished turn ends with a card of the files it edited (counts per file, the diffs, and Undo, which reverse-applies the turn's own hunks). `verify/live.mjs` checks all of it through the real frame against the scripted model (DEBUG builds).

## Spec, decisions, plans

The composable parts of docs/IDEATION-WORKFLOW.md (1, 5, 6), each usable alone (`backend/src/spec.rs`, `backend/src/plan.rs`, stages in `flow.rs`, rules and schemas in `backend/data/`):

- **Spec.** A message becomes the session's spec structurally (text longer than `limits.spec_min_chars` while there is none, or marked with the composer's Spec toggle) or by the router's `spec` field (`new`, `amend`). SPEC extracts the requirements (`R1`...) in one constrained call; SPEC_EDIT applies a later message's changes (added, dropped, changed ids; the id enum is the spec's own). Every change is a `spec` entry (a version); its number is its place among the `spec` entries in append order (corrected on the entry right after the append), so a user edit and a model amendment landing together get distinct versions, and SPEC_EDIT applies to the spec as it is after its model call. The model sees the current spec whole right after the system prompt (never folded, counted by the fit); its source message is shown as a reference. DECIDE and CHECKS get the open ids, the DO loop is asked to end with coverage per requirement. `chatflow.spec.update` (the spec card's edits) makes a version by the user; `chatflow.spec.save` writes `docs/specs/<slug>.md`.
- **Decisions.** The router's `settles` field runs DECISIONS after the answer: `decision` entries the user accepts or rejects (`chatflow.decision.answer`). Accepted ones join the spec (a version) or, without a spec, are pinned as the session's decision list, and are written to the project's knowledge as `decision` items (`memory.knowledge.upsert`; the entry keeps the `knowledge_id`; memory being away never fails the answer).
- **Knowledge** (docs/PROJECT-KNOWLEDGE-PLAN.md P2–P4; the store is the memory plugin's, on IronGraph). *Write side:* the router's `teaches` field (yes when the message states something durable about the project's world, or asks to remember) runs KNOWLEDGE after the answer and after DECISIONS: one constrained call (`schemas/knowledge.json`, `prompts/knowledge.md`) writes at most `limits.knowledge_items_per_turn` items (`kind` concept | fact | hypothesis | question, `name`, `text`, `state`, `binds`); the `binds` pick is filled by the host with the code the turn saw (`flow::turn_binds`: the route's symbols and files, the host's symbol, outline and file reads, the model's own `read` and `edit` paths, never a URI), so an item never names code nobody looked at, and the host keeps a `state` only when the kind allows it. Each item is kept at once (no card): written with `source: user`, its `knowledge` journal entry as evidence and `implemented_by` (a concept) or `about` links to its bound code; the entry keeps its `knowledge_id`. *Read side:* (1) what is bound to the code a host read serves rides along with it, one line per item appended to the read's output (`reads::knowledge_lines`, `memory.knowledge.linked` by the symbols' sids, or the outline's and file read's path; the tools plugin does the same for the model's own `read`, and serves `knowledge://<id>`); (2) after ROUTE (before a change's plan, or after a DECIDE read round), one `memory.knowledge.search` with ROUTE's `work` sentence, at most `limits.knowledge_per_turn` items, and the lessons that fit (`learn::recall`, at most `limits.lessons_per_turn`), as one host note (`purpose: knowledge`, `flow::knowledge_note`, the lessons shown in its `lessons`), items whose text the brief already holds left out, nothing when nothing is found; (3) the brief: `memory.knowledge.brief` within `limits.brief_tokens` (0 = none) in the byte-stable system prompt (`section_knowledge`, after the style, before the repository map), computed once per session with the rest of the prefix, so it is cached and prewarmed and the next session sees what was learned since.
- **Learning** (`learn.rs`, docs/LEARNING-REVIEW-2026-10-19.md). Every finished run (a foreground turn, an agent run) is queued to one worker. The host cuts its episodes from the journal with no model call (a refused call and the next call of that tool that worked; a command failing the same way twice and the different call that worked; a failing command that passed again after edits; an attempt that ended done, reported wrong and fixed by this run; a steer), at most `limits.learn_episodes_per_run`, each a short card in host words (`learn_*` texts). One LEARN call per card (`prompts/learn.md`, `schemas/learn.json`: `useful`, `anchor` from the episode's tools and languages or `approach`, `kind`, one sentence), at idle priority (`model.chat` `idle_only`: it starts only while the model serves nothing else, in a free slot, and leaves nothing in the pool). A lesson naming the project (its folder, a touched file, a type or code-shaped symbol of one) is about the project: it is kept as a project `fact`, named by its anchor. The rest are global `lesson` knowledge items, named `<anchor>: ...`, merged into a stored one at `limits.lesson_merge_score`. A lesson learned from a refusal or a failing command carries the failure's key as an alias (`learn::failure_key`: `refused <tool> <kind>`, or `failed <shape of the first error line>` with paths, quoted names and numbers taken out, `typeerrors::error_shape`); when that failure comes again in any run, the agent loop puts the lesson (and a project fact with that key) in a `lesson` note right under it, at most `limits.lessons_per_failure` (`learn::at_failure`). A stuck task's fresh start carries the same for its still-failing commands, and the skills the dropped attempt's errors brought. Lessons shown to a run get a verdict, kept on the run's `learned` note: `hurt` when their error came back; `helped` only in a run that ended done, for one shown under a failure that did not come again, or for the only lesson shown with the knowledge note whose anchor the run exercised (its tool used, a file of its language touched); `confounded` when several share that; `no observed effect` otherwise. Only `helped` and `hurt` count (`memory.knowledge.count`); hurt more than helped after three counts withdraws one. The run's `learned` note marks it (`Learned N items.` when it kept any); after each run up to `limits.learn_backlog_runs` earlier unmarked runs are learned, newest sessions first.
- **Replay gate and night report** (`replay.rs`, `night.rs`). A turn in a git workspace keeps its starting point in the plugin's data folder (`snapshots/`: the commit, the uncommitted diff, the untracked files git does not ignore; read-only git only; the newest 40). With nothing left to learn and no run going, the learner replays one live lesson whose run has a snapshot, taking turns between INV (`tool:`, `approach`) and DOM (`lang:`): the run's message is sent in two new sessions on fresh copies of the snapshot (`replays/`), one showing the lesson first with the knowledge note, one never showing it (a `replay` note marks the arm; replays ask nobody for approval and are not learned from). `with` done and `without` not is `helped`, the reverse `hurt`; the lesson gets a `replay://` evidence either way, and a user's turn cancels a replay (tried again later). Once a day the learner writes `reports/night-<date>.md`: the lessons proposed for a stronger form (a section in a skill: helped 3 times, never hurt; a host repair: a refusal's lesson that helped 5 times), the replays since the last report, and the lessons close to withdrawal. The report proposes; the owner applies.
- **Planned changes.** A decided change (DECIDE's DO) is planned before it is made: the PLAN stage runs with `plan_auto_live` (its tasks are carried out at once, one per run of the DO loop, by the conversation's own loop), the plan entry is recorded as `implementing` with the run as `implement_run`, and the Act stage makes the plan's tasks memory tasks under a root task (`materialize_plan_tasks`, the same records the agents path uses: the board and the cards show them) and runs them one at a time in order (`Stage::Act { step }`): each loop gets its task's title and brief and what the earlier tasks did (`agent_loop::step_live`, `do_step`, `do_task_text`), the task's contract (the last one's joined by the decision's checks) is verified before the next starts, the model's reply ends the task, its outcome is recorded on the plan entry (`steps_done`: the chat card marks done, failed and current tasks) and on the memory task (`memory.task.update`). A plan without tasks, or an IMPLEMENT decision (made from a plan), runs as one loop.
- **Ideation** (part 4, `backend/src/ideation.rs`). Route IDEATE (an open design question: options to choose from) runs in small steps around the host: the host grounds the question (a graph search for ROUTE's `work`, the files and symbols it names, the knowledge note, earlier research notes as one host note); IDEAS (`schemas/ideas.json`) writes the question, its constraints and criteria and one idea per principle, the principles being the schema's field names (`first`, `two_choices_flipped`, `constraint_relaxed`, `inverted`, `component_removed`, `borrowed`, `prior_art`) so the ideas differ by construction; the host looks every idea up (`memory.search`, `memory.note.search`; a web search by idea name was dropped: its hits were unrelated repositories the model then cited) and writes the `ideation` entry (`phase: ideas`), shown to the model as host text with the findings under each idea; OPTIONS (`schemas/options.json`) writes a keep / drop critique of each idea, two or three options (each `grounding` a pick of the findings, never a made-up source), a radical option and a recommendation (`phase: options`, the turn's answer: the model reads it as its own message). ROUTE chooses no skills for IDEATE (its stages run no tools). The options card chooses (`chatflow.ideation.choose`: an accepted `decision` with `ideation_seq`, joined to the spec or the decision list and the project's knowledge) and then offers Plan it (a turn "Plan option B: ...").
- **Plans.** Route PLAN (ROUTE and DECIDE; ROUTE's `skills` serve the planner only) runs PLAN, or PLAN_EDIT while a plan is open: a `plan` entry with the document and a task graph (numbered dependencies on earlier tasks only, touches, checks from the project's verifiers, covered requirement ids, and the task's own `skills` from the session's catalog, capped by `limits.skills_per_turn`), nothing changed. An edit is a new version with its difference. `chatflow.plan.update` approves; Implement (`chatflow.plan.implement`, or the router's IMPLEMENT, offered only while a plan is open) runs a single task in the foreground loop with its contract and its skills, or makes memory tasks (each brief naming that task's skills) with contracts and dependencies under a root task and starts the ready ones with `agents.spawn`. The user edits an open plan on its card (`chatflow.plan.edit`: goal, approach, architecture, risks and the whole task list with titles, briefs, rules, files, order and dependencies; a new version `by: user`, back to draft, refused with `conflict` on an older base) or comments on it and on its tasks (`plan_comment` entries, `chatflow.plan.comment`); Revise (`chatflow.plan.revise`) sends the open comments as one user message, each under its task's number and title, in a turn whose route is PLAN with the plan named (no router call), so PLAN_EDIT writes the next version. The chat panel draws the spec card (pinned), decision cards, plan cards (task progress from `agent_spawned` / `verification`) and the ideas and options cards.

## Build and run

```sh
cd backend && cargo build --release && cargo test --release && cargo clippy --all-targets -- -D warnings
cd ui && npm ci && npm run build && npm test     # after the SDK is built (cd ../../ui/sdk && npm run build)
cortex-pack build plugins/chatflow                  # -> plugins/chatflow/target/chatflow-<version>-<target>.ccplugin
```

`cortex-pack build plugins/chatflow --install` packs the folder into a `.ccplugin` that the frame installs (`frame.plugins.install`), which hot-swaps the backend and the UI packages together; Settings > Plugins disables and enables the whole plugin.

## Verification

The mechanics are verified together with the agents plugin: ../agents/verify/mechanics.mjs (gate 1.6 G3), against deterministic test peers (../runtime-testpeers) through the real frame. Its section 15 is `verify/ideation.mjs` (spec, decisions, plan mode) and section 16 `verify/references.mjs` (cross-project references); each also runs alone.
